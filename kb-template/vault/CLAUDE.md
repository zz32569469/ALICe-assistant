# 工作知識庫 Schema

本檔是這個 Obsidian vault 的 **Schema**，說明三件事：知識庫怎麼組織、要遵守哪些慣例、以及各工作流程的觸發條件與限制（低頻流程的完整步驟在 `_meta/流程/`）。
設計理念見 [[_meta/LLM Wiki 構想]]；用詞與寫法的細則見 [[_meta/寫作風格指南]]。本檔會隨使用經驗調整，每次修改都要在 `wiki/log.md` 記一筆 `schema`。

**定位**：知識來源以「**分析現有專案的程式碼**」為主，外部文件為輔。目標是之後著手相關專案（包含新開專案）時，能從這裡查到可重用的架構、做法、用語與踩坑紀錄。

角色分工：
- **使用者**：決定要分析哪個專案、提出問題、審閱結果、決定是否回寫。
- **LLM**：負責撰寫與維護所有頁面，包含分析、萃取、分類、交叉連結、術語統一、索引與日誌。

## 1. 目錄結構

```
{{KB_PATH}}/
├── CLAUDE.md                  ← 本檔（Schema）
├── AGENTS.md                  ← 給 Codex 的轉址檔，指向本檔
├── _meta/
│   ├── LLM Wiki 構想.md       ← 原始設計理念（唯讀參考）
│   ├── 寫作風格指南.md        ← 用詞、句型、頁面結構細則
│   ├── templates/             ← 各類頁面模板
│   ├── 流程/                  ← 低頻流程的完整步驟（分析、查詢、匯入、健康檢查、分支流程頁、對外連結、回寫協作）
│   ├── scripts/               ← 維護用腳本
│   └── archive/               ← 被重寫前的舊版頁面、舊 log、`退役頁面/`；Obsidian 設為不索引
├── raw/                       ← 外部文件原文（不可變）
│   ├── assets/                ← 附件
│   └── inbox/                 ← 尚未處理的外部文件
├── wiki/                      ← 跨專案可重用的知識（依技術領域分資料夾）
│   ├── index.md               ← 全庫目錄（查詢入口）
│   ├── 術語表.md              ← 標準用語對照（寫作前必查）
│   ├── overview.md            ← 全庫總覽與綜合結論
│   ├── log.md                 ← 時間序日誌（append-only）
│   ├── <領域>/                ← 依技術領域分資料夾；新增前先問使用者
│   ├── 知識庫工具/            ← Obsidian 與 LLM Wiki 方法
│   ├── AI 協作/               ← AI agent 工作流程；入口頁放領域根目錄，其餘依子資料夾分類
│   │   ├── 工具/              ← Claude Code、Codex 等工具頁（tag `工具/…`）
│   │   ├── 委派/              ← 委派流程（tag `流程/委派`）
│   │   ├── 驗收/              ← 驗收與快照（tag `流程/驗收`）
│   │   ├── token 管理/        ← token 節省（tag `流程/token`）
│   │   └── 角色/              ← 各 session 角色的職責與交接（tag `流程/角色`）
│   ├── 來源/                  ← 每次專案分析的快照、外部文件摘要
│   └── 分析/                  ← 查詢後回存的比較、決策紀錄
└── 專案/<project>/            ← 單一專案的操作指南（只放專案特有細節）
    └── <流程群>/<分組>/       ← 分支流程頁，見 §3.4
```

規則：
- `raw/` 絕不修改、刪除、改名。唯一允許的操作是把處理完的檔案從 `raw/inbox/` 移到 `raw/` 的子資料夾，並在 log 記錄。
- 被分析的專案 repo 一律**唯讀**，除非使用者明確授權。
- 新增領域資料夾前先問使用者，並同步更新本檔 §1、§3 的領域清單與 `wiki/index.md`。

## 2. 兩層知識的分工

| 層 | 放什麼 | 不放什麼 |
| --- | --- | --- |
| `wiki/<領域>/` | 跨專案成立的知識：概念定義、工具用法、實作模式、通用踩坑 | 某專案的檔案路徑細節、某個案例的數值 |
| `專案/<project>/` | 該專案的操作指南：要改哪些檔、步驟、驗證方式、專案特有的注意事項 | 通用原理（改成連到 wiki 頁） |

判斷方式：換一個專案這段內容還成立嗎？成立就放 wiki，專案頁只留一行摘要加連結；不成立就留在專案頁。
**同一段說明只寫在一處**，其他地方一律用連結，避免多處拼湊造成版本不一致。
團隊文件的規則與檢查清單每個專案都適用，寫在 wiki；某件工作做到哪裡、逐項結果寫在知識庫外的工作紀錄。

## 3. 頁面類型與命名

### 3.1 頁面類型（frontmatter `type`）

| type | 位置 | 用途 | 命名 |
| --- | --- | --- | --- |
| `concept` | `wiki/<領域>/` | 概念定義與原理 | 標準名稱（見 §4） |
| `tool` | `wiki/<領域>/` | 函式庫、框架、服務、軟體 | 官方名稱，例 `Obsidian.md` |
| `pattern` | `wiki/<領域>/` | 可重用的實作做法 | 中文描述性名稱，例 `IPC 通道設計.md` |
| `source` | `wiki/來源/` | 專案快照或外部文件摘要 | `YYYY-MM-DD 標題`，例 `2026-01-01 <專案> 程式碼快照.md` |
| `analysis` | `wiki/分析/` | 查詢回存 | 問題的簡短描述 |
| `project` | `專案/<project>/00-總覽.md` | 專案 MOC | 固定 `00-總覽` |
| `guide` | `專案/<project>/` | 操作指南 | `NN-動詞開頭的任務名`，例 `03-新增 API 端點.md` |
| （工作紀錄） | **知識庫外**：該工作的資料夾（例 `{{WORKSPACE}}/<工作資料夾>/`） | 某件工作的更改紀錄（每次修改，寫法見模板 `_meta/templates/更改紀錄頁.md`）、調整紀錄、流程檢查、交接文件。知識庫只留流程、順序與注意事項，並在專案指南寫這些檔案的路徑 | `<工作名> 更改紀錄` 等 |
| `glossary` / `overview` / `index` / `log` | `wiki/` | 系統頁 | 固定名稱 |

- 檔名避免 `/ \ : * ? " < > |`；同名頁只能有一個（Obsidian 以最短路徑連結）。唯一例外是專案的固定頁名（`00-總覽`、`99-注意事項與待確認`），連到它們時**一律寫完整路徑**，例 `[[專案/<專案>/00-總覽|<專案> 總覽]]`。
- 同一事物只開一頁，別名放 `aliases`，不另外開頁。
- 專案指南固定以 `99-注意事項與待確認` 收尾。

### 3.2 Frontmatter

```yaml
---
type: concept            # 見 3.1
title: <標準名稱>
aliases: [<指定中文稱呼>, <其他寫法>]
domain: <領域>           # 所屬領域資料夾名；專案頁填 專案
tags: [技術/<技術>]
projects: [<專案>]       # 本頁知識出現在哪些專案（純文字，方便 Dataview）
sources: ["[[<來源頁>]]"]
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: stub | draft | stable
---
```

- `status`：`stub` 只有定義；`draft` 來自單一專案或單一來源；`stable` 已綜合兩個以上的專案或來源。
- 專案頁另加 `project: <name>`，guide 頁另加 `basis: <commit 短 hash>`（分析時的程式碼版本）。
- 選填關聯欄位（Obsidian 會把屬性中的連結算進反向連結與關聯圖）：
  - `up: "[[上層頁]]"`：所屬的入口頁（例：AI 協作各頁 `up` 指向 `[[Claude Code 與 Codex 分工]]`），入口頁本身留空。
  - `related: ["[[頁]]", …]`：同層級的相關流程或工具。
  - `AI 協作` 領域必填，其他領域選填。
- **領域內分類**（頁面變多的領域）：子資料夾、tag、頁面關聯三者並用。頁名仍需全庫唯一，連結只寫頁名，搬移資料夾時連結不失效。

Tag 分類（新增時同步更新此清單）：
- `技術/…`：例 `技術/TypeScript`、`技術/Git`
- `領域/…`：依業務領域自訂
- `專案/…`：每個專案一個
- `工具/…`：`工具/Obsidian`、`工具/Claude Code`、`工具/Codex`
- `流程/…`：`流程/分工`、`流程/委派`、`流程/驗收`、`流程/token`、`流程/角色`

### 3.3 內文結構

每種類型的固定章節見 `_meta/templates/`，共通規則：
- 開頭用 `> ` 引言，1–3 句說明「這是什麼、為什麼重要」。
- 第一次提到有頁面的概念、工具或模式時就加 `[[連結]]`。
- 關鍵主張後附來源：`（[[<來源頁>]]）`，或程式碼位置 `` `src/main.ts:725` ``（行號以該頁 `basis` 版本為準）。
- 矛盾用 `> [!warning] 矛盾`，待查用 `> [!question] 待查`，踩坑用 `> [!danger] 注意`。
- 被取代的舊說法移到 `## 歷史說法`，並註明被哪個來源取代。
- 頁尾固定有 `## 相關`。
- **以特定案例為例的內容**：內文標明案例名稱，頁首放 `> [!note] 規格只適用於該案例` 提示框，說明其中的規格、欄位與數值只適用該案例。

### 3.4 分支流程頁（專案層）

一件大工作拆成多條可單獨執行的分支流程時使用：放在 `專案/<project>/<流程群>/<分組>/`、命名 `<前綴>-<流程名>`（不用 `NN-`）、以輸入／產出契約描述。完整規範見 [[_meta/流程/撰寫分支流程頁]]，寫這類頁面前先讀。

## 4. 術語規範（避免用詞重複與模糊）

1. **標準名稱以程式碼用語為主**：與程式碼、設定檔中的識別字一致，中文與其他寫法列為別名。別名的第一個詞是內文可用的指定中文稱呼，其餘別名不得用於內文。
2. 沒有程式碼識別字的概念，才用最通用的中文名稱。
3. `wiki/術語表.md` 是唯一權威。**撰寫或修改任何頁面前先查術語表**；遇到表中沒有的詞，先加入術語表再使用。
4. 同一概念在程式碼中有多種寫法時（例 `fetch` / `load` / `get`），術語表要列出全部寫法並選定一個標準名稱，內文一律用標準名稱。
5. 業界常見意義與專案內意義不同時，必須在術語表標註。
6. 內文用詞規則與句型見 [[_meta/寫作風格指南]]。

## 5. 工作流程

有連結的流程，執行前先讀該頁；本檔只留觸發條件與必須遵守的限制。

| § | 流程 | 觸發 | 必須遵守 | 步驟 |
| --- | --- | --- | --- | --- |
| 5.1 | Analyze（主要流程） | 「分析 <專案>」「更新 <專案> 的知識」 | 第一次分析專案前先確認範圍與重點（使用者說「批次／不用問」時跳過） | [[_meta/流程/分析專案]] |
| 5.2 | Query | 提問、`/kb` | 唯讀；查不到要明說；跨很多頁彙整可找知識庫管理員 | [[_meta/流程/查詢]] |
| 5.3 | Write-back | 階段結束、待回寫滿 10 則、使用者說「回寫」 | 專案 session 不直接寫；候選先累積在工作紀錄，整批交給「知識庫管理員」session 共同整理，使用者同意後由管理員寫入，並做 §9 檢查；log 記 `writeback`（註明發起專案） | [[_meta/流程/回寫協作]] |
| 5.4 | Ingest | `raw/inbox/` 有新文件 | 圖片規則見流程頁 | [[_meta/流程/匯入外部文件]] |
| 5.5 | Lint | 「lint」「健康檢查」、§9.8 的時機 | 先產出報告，確認後才修正；完成後 log 記 `lint` | [[_meta/流程/健康檢查]] |

## 6. index.md 與 log.md 格式

**index.md**：依「系統頁 / 專案 / 各領域 / 來源 / 分析」分區，每行：
```
- [[頁面]] — 一句話摘要（type，status，更新 YYYY-MM-DD）
```

**log.md**：append-only，不改寫舊紀錄：
```
## [YYYY-MM-DD] <analyze|query|writeback|ingest|lint|schema|init> | 標題
- 新增：[[…]]
- 更新：[[…]]
- 備註：…
```
每筆最多 3 行，備註一句，不重述頁面內容（§9.5）。
查最近紀錄：`grep "^## \[" wiki/log.md | tail -5`

log 變長時，把較舊的整段條目原樣搬到 `_meta/archive/log <起>～<迄>.md`（不改寫內容），並在 log.md 開頭引言列出封存檔連結。

## 7. 對外連結

全域指引、`/kb` skill 與 Codex 轉址檔的位置見 [[_meta/流程/對外連結]]。修改本檔的流程時，先讀該頁檢查要同步的地方。

## 8. 其他

- 規模小時以 index 導航即可；頁面多到難以用 index 查找時，再導入本地搜尋工具，並記錄到本檔。
- 建議外掛：Dataview（frontmatter 查詢）。

## 9. 維護規範（長度與單一來源）

> 目的：減少每次工作要讀的量、避免同一件事寫在多處而不一致。回寫（§5.3）與健康檢查都要檢查本節。

### 9.1 單一來源
- 某件工作的量測數據、調整結果與進度，只寫在知識庫外的工作紀錄。知識庫寫規則、原理與流程；需要例子時最多一句（附日期），並寫紀錄檔路徑。
- 同一段說明只寫在一處（§2）。回寫前先 Grep 有沒有頁面已經寫過：有就擴充那一頁，其他頁最多一行「見 [[…]]」。
- 一次回寫要改 3 頁以上時，先確認是不是在重複同一件事。

### 9.2 長度上限

| 頁面 | 上限（UTF-8 位元組，`wc -c`） |
| --- | --- |
| 本檔 | 2 萬（接近上限時，把低頻流程的細節移到 `_meta/流程/`） |
| `wiki/<領域>/` 頁 | 2 萬 |
| `專案/<project>/` 指南 | 2.5 萬 |
| `wiki/log.md` | 3 萬，超過就依 §6 封存 |
| 術語表、index | 不設上限，依 §9.3 查 |

- 用位元組量是因為約 3 位元組 = 1 token（中英文皆然）。
- 寫入後超過上限：同一次工作內先拆（依主題拆成子頁；原位置保留標題並留一行連結，既有的 `#標題` 連結才找得到）。不知道怎麼拆時問使用者。
- 已經超過上限的頁，下次寫入前先拆。

### 9.3 讀取方式
- 術語表、log 用 Grep 查需要的列，不整份讀；index 在 Query 時可以整份讀。
- 超過 1 萬位元組的頁，先 Grep 標題（`^#`）定位，只讀需要的段落；要照頁內檢查清單做事時才整頁讀。

### 9.4 程式位置
- `檔案:行號` 以該頁 frontmatter 的 `basis` 為準；引用不同分支或未提交的版本時，註明分支或 commit。
- 行號旁加函式或條件名稱，例 `src/app.ts:120`（`if (!user)`），行號漂移時才能用名稱找回。
- 同一段程式在不同頁引用時，行號要一致，或各自註明分支。

### 9.5 log
- 每筆最多 3 行：標題、新增／更新的頁（每頁附 3～10 字說明）、一句備註。

### 9.6 記憶與知識庫
- Claude 的自動記憶只放使用者偏好、決定與知識庫外的指標。知識庫已經寫的規則，記憶只留一行「見知識庫〈頁名〉」與為什麼重要，不複製內容。

### 9.7 session 工作目錄
- 做專案工作時，session 開在該專案的目錄（例 `{{WORKSPACE}}/<專案>`），透過全域指引與 `/kb` 查知識庫；只有維護知識庫本身時才開在 vault。本檔只在 vault 目錄自動載入，開在 vault 做專案工作會一直占用上下文。
- 專案 session 開在專案主目錄，不用 App 的 worktree：worktree session 不能直接修改主目錄的檔案，而驗證腳本多半指向主目錄（[[Claude Code#注意事項]]）。
- 開在 vault 的 session 是 [[知識庫管理員]]（session 名稱 `Library`）；各角色的 session 名稱與開在哪裡見 [[Claude Code 與 Codex 分工#角色]]。
- 開背景任務（新 session）時同樣指定專案目錄。

### 9.8 健康檢查時機
- 自上次 `lint` 後累積 10 筆以上 `writeback`／`ingest`，或超過 7 天，在回報時提醒使用者跑健康檢查。
