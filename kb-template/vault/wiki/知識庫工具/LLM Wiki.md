# LLM Wiki

> LLM Wiki 是讓 LLM 持續撰寫與維護一組互相連結的 Markdown 頁面的知識管理做法。和每次查詢才檢索原文的 RAG 不同，知識在納入時就被整理、交叉連結並標出矛盾，之後越用越完整（[[_meta/LLM Wiki 構想]]）。

## 解決什麼問題

- RAG 每次查詢都從原文重新拼湊答案，沒有累積。
- 人工維護 wiki 時，交叉連結、同步摘要、標註矛盾的負擔成長得比價值快，最後放棄維護。

## 做法

### 三層結構

| 層 | 內容 | 誰維護 |
| --- | --- | --- |
| 原始來源 | 文件、文章、資料；不可變 | 人蒐集 |
| wiki | 摘要、概念頁、實體頁、比較、總覽 | LLM |
| schema | 規範文件（如 `CLAUDE.md`），定義結構、慣例與流程 | 人與 LLM 共同演進 |

### 三種操作

| 操作 | 內容 |
| --- | --- |
| Ingest | 納入新來源：寫摘要、更新相關頁、更新 index、記 log；一份來源常觸及 10~15 頁 |
| Query | 先讀 index 找頁面再綜合回答；有價值的答案回存成新頁 |
| Lint | 定期檢查矛盾、過時主張、孤兒頁、缺頁的概念、失效連結 |

### 導航檔

- `index.md`：依類別列出所有頁面與一句話摘要，LLM 查詢時先讀它。在約 100 份來源、數百頁的規模內可取代向量檢索。
- `log.md`：append-only 時間序紀錄，每筆以固定前綴開頭（`## [YYYY-MM-DD] 類型 | 標題`），可用 `grep` 取最近紀錄。

## 範例

### 本知識庫

本 vault 依此做法建立，並做了以下調整：

| 原始構想 | 本知識庫的調整 |
| --- | --- |
| 來源以文章、論文為主 | 以**分析現有專案程式碼**為主，外部文件為輔 |
| wiki 依頁面類型分資料夾（entities / concepts） | 依**技術領域**分資料夾，類型寫在 frontmatter |
| 未規範用語 | 新增[[術語表]]與寫作風格指南，標準名稱以程式碼用語為主 |
| 只在 vault 內使用 | 透過全域 `CLAUDE.md` 與 `/kb` skill，讓其他專案也能查詢與回寫 |
| — | 新增「專案操作指南」層，只放專案特有細節 |
| — | 知識庫寫入集中由「知識庫管理員」session（名稱 `Library`） 執行，其他 session 批次提出回寫候選（[[_meta/流程/回寫協作]]） |

## 取捨

| 優點 | 缺點 |
| --- | --- |
| 知識累積、交叉連結自動維護 | 規模變大後 index 不足，需要本機搜尋工具 |
| 答案可回存，探索也能累積 | LLM 寫錯的內容會被後續引用，需要人審閱與定期 lint |

## 注意事項

- schema 是讓 LLM 成為「有紀律的維護者」的關鍵；流程改變時要同步更新 schema。
