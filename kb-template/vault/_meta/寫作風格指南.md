# 寫作風格指南

> 所有 wiki 頁與專案頁的寫法細則。目的是讓不同時間、不同專案寫出來的頁面讀起來像同一個人寫的，避免同一件事有好幾種說法。
> 規範總綱見 `CLAUDE.md`；標準用語見 [[術語表]]。

## 1. 語言

- 內文用**繁體中文**；程式碼識別字、檔名、產品名保留原文，並用行內程式碼標示：`<套件名>`、`src/main.ts`。
- 產品名與框架名不加程式碼標記：Vue、Vite、Obsidian。
- 中英文之間不強制加空格，但同一頁要一致；數字與單位之間不加空格（`10次`、`400MB`）。
- 標點用全形（，。：；「」），程式碼與路徑內保留半形。

## 2. 用詞

- **只使用 [[術語表]] 允許的兩種寫法**：標準名稱，或別名欄的**第一個詞**（指定中文稱呼，括號內可註明簡稱）。例：`<識別字>` 或它的指定中文稱呼都可以；其他別名不可用於內文。
- 講概念本身、或與程式碼對照時用標準名稱；敘述流程時可用指定中文稱呼。第一次出現建議兩者並列：`<識別字>`（中文稱呼）。
- 其他別名只能出現在術語表與頁面 `aliases`。
- 禁止在同一頁混用同義詞，例如「取得 / 載入 / fetch」只能擇一（依術語表）。
- 避免模糊詞：「某些」「相關的」「一些處理」「等等」。要嘛列出具體項目，要嘛寫「共 N 項，見 …」。
- 避免主觀形容：「很棒」「非常重要」。改寫成具體影響：「若漏改，報表會顯示空白」。
- 不確定的事寫成 `> [!question] 待查`，不要用「應該」「可能」帶過。

## 3. 句型

- 一句只講一件事，長句拆開。
- 說明行為用「主詞 + 動作 + 結果」：「`build.cjs` 讀取 `config.json`，產生缺少的模組檔。」
- 操作步驟用祈使句並編號：「1. 在 `config.json` 加入 …」。
- 條件寫在前面：「打包環境下，路徑以 `process.cwd()` 為基準。」

## 4. 頁面結構

各類型固定章節（模板見 `_meta/templates/`）：

| type | 章節順序 |
| --- | --- |
| concept | 引言 → 定義 → 運作方式 → 在專案中的實作 → 注意事項 → 歷史說法 → 相關 |
| tool | 引言 → 基本資訊表 → 核心用法 → 在專案中的用法 → 注意事項 → 相關 |
| pattern | 引言 → 解決什麼問題 → 做法 → 範例（附專案出處）→ 取捨 → 注意事項 → 相關 |
| guide | 引言 → 適用情境 → 前置知識 → 步驟 → 涉及檔案 → 驗證方式 → 注意事項 → 相關 |
| source | 引言 → 基本資訊 → 範圍 → 主要發現 → 產出頁面 → 相關 |

- 標題層級：頁內從 `##` 開始，最多到 `####`。
- 「在專案中的實作」一節用小標題區分專案：`### <專案名>`，第二個專案出現時再加一節，**不另開頁**。

## 5. 程式碼位置與範例

- 路徑相對於專案根目錄：`src/worker.ts:62`。
- 行號以頁面 frontmatter 的 `basis` commit 為準；程式碼更新後由 lint 檢查。
- 範例程式碼只保留說明所需的最少行數，並標示語言（```ts）。不整段複製原始碼。

## 6. 表格、清單與圖

- 三個以上的並列屬性用表格；步驟用編號清單；無順序的項目用 `-`。
- 資料流、呼叫順序用 Mermaid `flowchart` 或 `sequenceDiagram`，節點名稱用標準名稱。

## 7. Callout 與標記

| 用途 | 寫法 |
| --- | --- |
| 踩坑、容易出錯 | `> [!danger] 注意` |
| 新舊資料衝突 | `> [!warning] 矛盾` |
| 待確認、缺資料 | `> [!question] 待查` |
| 補充說明 | `> [!note]` |

風險清單的嚴重度（僅用於 `99-注意事項與待確認`）：
- 🔴 可能造成錯誤結果或無法運作
- 🟠 特定情境出錯或行為待確認
- 🟡 維護性或文件問題

內文其他地方不使用 emoji。

## 8. 連結

- 連 wiki 頁用頁名：`[[<頁名>]]`；需要換顯示文字時用 `[[<頁名>|顯示文字]]`。
- 連專案頁用完整路徑，避免同名：`[[專案/<專案>/03-新增 API 端點|新增 API 端點]]`。
- 連到章節：`[[<頁名>#<章節>]]`。
