# 分析專案

> 執行這個流程前先讀本頁。規範仍以 `CLAUDE.md` 為準，修改本頁與修改 Schema 相同，要在 `wiki/log.md` 記一筆 `schema`。

觸發：「分析 <專案路徑>」、「更新 <專案> 的知識」。

1. **確認範圍**：專案路徑、分支與 commit、這次要涵蓋的模組。記下 `git rev-parse --short HEAD`、與遠端的差距、未提交修改。
2. **閱讀**：先讀 README / AGENTS.md / package.json 等文件，再依資料流讀原始碼；不確定的行為不要猜，列入待確認。
3. **建立快照頁**：`wiki/來源/YYYY-MM-DD <專案> 程式碼快照.md`，記錄版本、範圍、技術棧、閱讀過的檔案、主要發現。
4. **萃取通用知識**：找出可跨專案重用的概念、工具與模式，新增或更新 `wiki/<領域>/` 頁。更新前先查術語表與既有頁面，**擴充既有頁面優於新開頁面**；與舊內容衝突時加 `[!warning] 矛盾`。
5. **撰寫專案指南**：在 `專案/<project>/` 以「要完成某件事時該怎麼做」為主軸撰寫 guide 頁；架構只保留理解指南所需的最少說明，風險寫進各指南的「注意事項」，完整清單彙整在 `99-注意事項與待確認`。
6. **更新術語表**：新詞加入、既有詞補上本專案的寫法。
7. **更新** `wiki/index.md`、`wiki/overview.md`，並在 `wiki/log.md` 記一筆 `analyze`。
8. **回報**：新增與修改的頁數、新術語、矛盾、待確認事項。

第一次分析專案前先和使用者確認範圍與重點；使用者說「批次 / 不用問」時跳過。
