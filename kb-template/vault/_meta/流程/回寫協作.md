# 回寫協作

> 專案 session 發現值得保存的知識時，不自己寫入知識庫，而是找「知識庫管理員」session（名稱 `Library`） 共同整理：專案 session 提供前因後果，管理員檢查單一來源、術語與長度後寫入。規範仍以 `CLAUDE.md` 為準，修改本頁與修改 Schema 相同，要在 `wiki/log.md` 記一筆 `schema`。

## 角色

各 session 的職責見 [[Claude Code 與 Codex 分工#角色]]。本流程中：[[知識庫管理員]]執行**所有知識庫寫入**；專案 session（[[專案工程師]]）提出回寫候選並核對寫入結果；Codex 不寫知識庫，回寫候選列在回報中，由專案 session 轉交。

## 查詢

- 專案 session 自己查（全域指引「怎麼查」、`/kb`）。
- 需要跨很多頁彙整、或擔心讀太多占上下文時，才傳訊息給管理員。管理員回覆頁面路徑與需要的重點段落，知識庫沒有的明說。

## 回寫

### 累積與送出時機

回寫一次要經過提案、使用者同意、寫入、核對，逐則處理太打斷使用者，所以採**批次**：

- **平時**：候選先記在該工作的更改紀錄「待回寫」段落（知識庫外），不傳給管理員。每則寫前因後果、證據、判斷（格式同下方步驟 1）。
- **送出**：符合任一條件時整批傳給管理員：
  1. 一個階段結束（例：完成交付、一輪需求做完）。
  2. 待回寫累積到 **10 則**。
  3. 使用者說「回寫」。
- **例外，立即送**：會影響另一個角色正在做的事（分工或交界規則改變、兩個角色對同一規則寫法相反）。角色之間的變更通知（例：輸出格式變更通知）直接傳送，不屬於回寫。
- 送出後，把已送出的項目標「已送出 YYYY-MM-DD」；寫入完成再標「已寫入」。
- 編號：同一件工作的「待回寫」表由多個角色共用時，各用自己的前綴避免撞號（例：開發類 `D1、D2…`、文件類 `W1、W2…`）；已寫入的舊編號不改。

### 步驟

1. **專案 session 送出一批候選**：用 `ListAgents` 找知識庫管理員（session 名稱 `Library`），以 `SendMessage` 傳送（第一行寫「回寫候選 N 則」與一句話摘要），每則包含：
   - 前因後果：做了什麼、量到什麼（未量的標「未查證」）。
   - 證據：`檔案:行號`（函式或條件名稱，註明分支或 commit）、工作紀錄檔路徑。
   - 判斷：通用知識或專案特有。
2. **管理員提案**：依 `CLAUDE.md` §9 檢查（Grep 有沒有頁寫過、術語表、寫入後長度），整批回一份寫入提案：寫到哪一頁、寫什麼、要改的舊說法、不收的項目與原因。不清楚就反問專案 session。
3. **來回到定案**：回覆訊息時，`to` 用收到訊息的 `from` 屬性。
4. **使用者同意後寫入**：管理員向使用者提案**一次**，同意後寫入，更新 index（有新頁時）與 log（**一批一筆** `writeback`，備註寫發起專案）。
5. **核對**：管理員回傳改了哪幾頁，專案 session 核對一次；有錯就回報，由管理員修正。

- 某件工作的量測數據與進度只寫在知識庫外的工作紀錄（`CLAUDE.md` §9.1），候選訊息寫紀錄檔路徑即可。
- 專案指南與工作分配表也是知識庫頁面，修改同樣走本流程。

## 管理員 session 沒開時

- 到了送出時機但管理員沒開：候選留在「待回寫」並提醒使用者，下次開管理員 session 時一起處理。
- 專案 session 不自己寫入知識庫。

## 注意

- 兩個 session 的權限模式不同時，跨 session 訊息要使用者核准才送達；管理員 session 使用與專案 session 相同的權限模式。
- 傳送成功只代表送達，不代表對方已讀；沒有回覆不視為同意。
- session 重開後訊息位址會變，傳送失敗時用 `ListAgents` 以名稱重找。
