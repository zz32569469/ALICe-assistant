# 規格 ⑧：專案管理

> ALICe 當參謀兼秘書：主人直接找各同事 session（工程師）做事，ALICe 管多個專案的進度、等主人決定的事與提醒。

## 1. 專案卡

- 每個專案一張，存在 Core 資料庫（`games`、`game_stages`、`game_tasks` 表）。卡片可能含工作資料，只在本機，不進 git。
- 欄位：名稱、英文代號（分支名用）、品牌或分類、文件資料夾與檔名前綴、規格書位置、參考資料、截止日、版本與需求來源、每條進度線目前的階段、更改紀錄要讀的段落、相關 repo（本機設定 `projects[].name`）、同事 session、備註。
- 每次換階段各自記日期（`game_stages` 的 `track` 欄）。
- 建立與修改都在對話裡進行。ALICe 在回覆最後放 `ALICE_GAME` 區塊（一則可以有多個），Core 套用後留一則系統訊息：
  - `create`：新卡，每條線預設第一個階段，版本照流程設定的 `firstVersion`。
  - `update`：只寫要改的欄位；`stages: {"<線>":"<階段>"}` 換階段（只寫要換的線；只有一條線時可以寫 `stage`）；`newName` 改名；`deadline: null` 取消截止日。
  - 檢查：階段要在那條線的清單內（忽略空白、大小寫、頓號與斜線，也認流程設定的別名），日期要合法，代號只能英數字，版本是用點分開的數字，repos 只能用本機設定裡的專案名稱。
- **版本：** 每條線都到最後一個階段，這個版本就結束。之後有新需求時開新版本（`version`，版號要變大），`versionReason` 寫需求來源，再把要動的線移回對應階段。

### 1.1 流程設定

進度線與階段不寫在程式裡，由流程設定決定（`core/src/games/workflow.ts`）：

- **內建：** 一條線「進度」：規劃 → 進行中 → 驗證 → 完成。
- **自訂：** 在 `alice.local.json` 設 `workflowFile` 指向一個 JSON（本機檔，不進 git）。讀不到或格式錯時改用內建流程，並在 Web Studio 頂端顯示警告。

```json
{
  "tracks": [
    {
      "key": "build", "label": "開發",
      "stages": ["需求確認", "實作", "整合測試", "上線準備", "完成"],
      "aliases": { "寫程式": "實作" },
      "sessions": [{ "pattern": "\\s-\\s*dev 2$", "fromStage": "上線準備" }, { "pattern": "\\s-\\s*dev$" }],
      "guide": { "page": "開發工程師.md", "heading": "大階段", "rows": { "需求確認": "1", "實作": "2" } }
    },
    { "key": "docs", "label": "文件", "stages": ["等待實作", "撰寫", "審閱", "完成"] }
  ],
  "taskSources": ["需求", "回饋", "其他"],
  "firstVersion": "1.0.0",
  "rules": ["兩條線都到「上線準備」才一起上線。"],
  "newProjectQuestions": "專案名稱、代號、截止日、要用哪些 repo",
  "newProjectSteps": ["固定加一個任務「設計文件」。"],
  "meetingRules": ["- 和客戶的會議，列出等客戶確認的事。"]
}
```

| 欄位 | 說明 |
| --- | --- |
| `tracks[].key`／`label`／`stages` | 線的識別字、顯示名稱、依序的階段（最後一個是完成）。 |
| `tracks[].aliases` | 舊名稱或簡寫 → 階段，ALICe 寫錯或流程改名時對得上。 |
| `tracks[].sessions` | 負責這條線的同事 session：由上往下第一個符合的（不分大小寫的正規表示式；`fromStage` 表示到這個階段以後才換它）。 |
| `tracks[].guide` | 完成條件來源：知識庫角色資料夾裡的角色頁、表格所在標題（預設「大階段」）、階段對到表格的 `#`。Core 讀表格的「判定」「使用者決定」（或「主人決定」）欄。 |
| `taskSources` | 任務的需求來源。 |
| `firstVersion` | 新專案的版本號。 |
| `rules` | 加進「專案管理」提示的團隊規則。 |
| `newProjectQuestions`／`newProjectSteps` | 開新專案要一次問完的欄位、建卡後的固定做法。 |
| `meetingRules` | 會議段落的補充規則。 |

### 1.2 任務清單

- 每張卡有自己的任務清單，編號 T1、T2…。欄位：標題、負責（線的 key，或 `owner`＝主人）、狀態（待辦、進行中、卡住、完成、取消）、來源（流程設定的 `taskSources`）、版本、備註（最近一次更新的依據）。
- 寫法：`ALICE_GAME` 加 `tasks`，`{"op":"add",...}` 新增、`{"op":"update","id":"T3",...}` 修改；可以只改任務。一次最多 30 個操作。
- ALICe 可以直接新增任務、改成待辦／進行中／卡住／取消。**任務改成「完成」與換階段先給主人確認：** Core 把這部分保留成確認卡片並跳桌面通知，主人按「確認更新」才套用，按「先不要」就維持原狀。
- 任務從哪來：
  1. **同事回報：** 同事 session 開始、完成或卡住時，用 SendMessage 傳給 ALICe 一則第一行「【進度】<專案名稱>」的訊息。
  2. **每日核對：** 每天 9 點後第一次檢查時（一天一次；資料和上次一樣就不呼叫模型），請 ALICe 對照任務清單更新。
  3. **主人按「更新進度」**，或轉述新的需求。

## 2. 進度總覽

1. 主人問進度時，ALICe 回一句「我整理一下」，並放 `ALICE_PROGRESS` 區塊（`{"games":[...]}`；空陣列表示目前版本還沒完成的專案）。
2. Core 收集資料，不用推理：
   - **文件：** 文件資料夾內以前綴開頭的 `.md` 檔；預設擷取標題含「現況」或「待」（不含「待回寫」）的段落。
   - **git：** 各 repo 的目前分支、未提交檔數、名稱含代號的分支的最後提交與未推送數；專案分支切在其他 git worktree 時，讀那裡的未提交狀態。
   - **完成條件與負責：** 每條線一行「負責、完成條件、要主人決定」。
   - **Codex 任務：** 最近 7 天委派給 Codex 的任務。
3. ALICe 依格式整理：每個專案先一行結論，再列做完的、進行中、卡在誰、等主人決定的事；最後是跨專案要注意的事。資料裡沒有的寫「紀錄裡沒寫」。

## 3. 開新專案

主人說「開新專案 XXX」後，ALICe 一次問完缺的欄位（流程設定的 `newProjectQuestions`，或內建的一組），主人回答後建卡並開第一批任務。同事 session 由主人自己開。

## 4. API

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| GET | `/api/games` | 專案卡（含每條線的階段、換階段歷史、任務、負責與完成條件、最後動靜）、`tracks`（流程設定的線與階段）、`taskSources` |
| POST | `/api/games/refresh` | 請 ALICe 依任務清單核對各專案進度 |
| GET | `/api/games/confirmations` | 等主人確認的進度變更 |
| POST | `/api/games/confirmations/:id/approve`、`/reject` | 確認或不要 |

WebSocket 事件：`games.updated`、`game.confirmation.created`、`game.confirmation.resolved`。

## 5. Web Studio

工作面板第一個分頁「專案」：每張卡片顯示版本、每條線的進度條（目前階段、第幾階段、開始日期、完成條件、下一步與負責的 session）、未完成任務、截止日倒數、最後動靜。卡片可以收合。建立、修改都在對話裡跟 ALICe 說。
